[DuckLake](https://ducklake.select) stores table data as Parquet
files in object storage and hosts its catalog in a SQL database: SQLite,
Postgres, or DuckDB served over [Quack](https://duckdb.org/quack/). That
provides transactional consistency and ACID guarantees, but forces all
writes to go through the catalog database.

Moraine instead hosts that catalog database in [SlateDB](https://slatedb.io), a
transactional key-value store that also lives in object storage. The
catalog sits in the bucket beside the data files. DuckLake's SQL runs
against it unchanged.

```sql
LOAD 'moraine.v2.0.0.linux_amd64.duckdb_extension';

CREATE SECRET s (TYPE s3, KEY_ID '…', SECRET '…', REGION 'us-west-2');
ATTACH 'ducklake:moraine:s3://bucket/lake' AS lake
  (DATA_PATH 's3://bucket/lake-data/', READ_WRITE);

CREATE TABLE lake.events (id BIGINT, payload VARCHAR);
INSERT INTO lake.events VALUES (1, 'hello, bucket'), (2, 'hello again');
SELECT * FROM lake.events;

CREATE UNIQUE INDEX events_by_id ON lake.events (id);
SELECT payload FROM lake.events WHERE id = 2;
```

## What you get

- **No catalog server:** No catalog server to deploy or monitor. A deployment
  is a storage bucket.
- **Bucket durability:** The catalog is objects in the bucket, so it gets
  the bucket's durability, replication, and versioning. A copy taken while
  no writer is attached is a complete lake; see
  [Backups and copies](guide/operating/#backups-and-copies).
- **Nothing to pay for while idle:** An idle lake costs only storage, no
  compute or database hosting fees.
- **Indexed lookups:** Ordered indexes over table columns, created with
  `CREATE INDEX` and maintained in the same commit as the rows, so a query
  by key probes the index instead of scanning every file; see
  [Index a column](guide/getting-started/#index-a-column).

## When not to use Moraine

- **Sub-5 ms commits.** A commit is durable once one write-ahead-log PUT
  lands: 50 to 100 ms on S3 Standard, 5 to 10 ms with the log on S3 Express
  One Zone via
  [`META_WAL_PATH`](guide/configuration/#the-write-ahead-log-on-a-faster-bucket).
- **Many independent writer processes.** One process writes; the rest
  attach `READ_ONLY`. See
  [one writer, many readers](guide/getting-started/#one-writer-many-readers).
- **A signed extension, today.** Not yet in DuckDB's community repository:
  it loads with `-unsigned`, one build per DuckDB version.

## By the numbers

Identical DuckLake workloads through the same DuckDB CLI, only the catalog
swapped. Local disk, loopback Postgres 16, medians of three runs on an
8-vCPU x86-64 VM:

| | Moraine | DuckDB file | Postgres |
|---|---:|---:|---:|
| attach | 8 ms | 19 ms | 113 ms |
| create table and insert 100,000 rows | 94 ms | 102 ms | 124 ms |
| 20 single-row commits, one connection | 254 ms | 218 ms | 135 ms |
| 128 single-row commits over 8 connections | 417 ms | 1.76 s | 1.77 s |
| 128 single-row commits over 16 connections | 461 ms | 2.85 s | 2.94 s |

Serial commits pay a write-ahead-log flush each, where a local Postgres is
faster. Overlapping commits share one flush. On S3, each flush is one PUT
round trip, about 30 ms same-region. For more details, see
[Benchmarks](benchmarks/).

## Status

Moraine is under active development and in production use at
[contour.app](https://contour.app). DuckLake SQL, including `CREATE`,
`INSERT`, `UPDATE`, `DELETE`, time travel, and maintenance, runs against
Moraine as its catalog and is validated against real DuckDB in CI. The
[roadmap](roadmap/) lists what is done and what is next. Questions go to
[GitHub Discussions](https://github.com/morainedb/moraine/discussions).
