## Cost considerations

The smallest single-AZ RDS Postgres (`db.t4g.micro`, 20 GB gp3, us-east-1)
is $0.016 an hour plus $0.115 per GB-month: about $14 a month, idle or not,
before backups or Multi-AZ.

A 100 MB Moraine catalog on S3 Standard costs $0.0023 a month to store. A
writer committing once a minute adds about $0.22 in PUTs and about as much
in compaction. A reader polling every ten seconds adds at most $1.30
at the LIST price, $0.22 at once a minute.

## Scheduled maintenance

The writer can run DuckLake's maintenance functions on a schedule. Enable
the pass and the steps at attach:

```sql
ATTACH 'ducklake:moraine:s3://bucket/prefix' AS lake
  (READ_WRITE,
   META_MAINTENANCE_INTERVAL INTERVAL 10 MINUTE,
   META_MAINTENANCE_EXPIRE_SNAPSHOTS_OLDER_THAN INTERVAL 7 DAY,
   META_MAINTENANCE_FLUSH_INLINED_DATA true,
   META_MAINTENANCE_MERGE_ADJACENT_FILES true,
   META_MAINTENANCE_CLEANUP_OLD_FILES_OLDER_THAN INTERVAL 7 DAY);
```

| Option | Meaning |
|---|---|
| `META_MAINTENANCE_INTERVAL` | Enables scheduled maintenance; sets the interval between passes. |
| `META_MAINTENANCE_<STEP> true` | Enable a step with DuckLake's defaults. |
| `META_MAINTENANCE_<STEP>_<PARAMETER> value` | Enable the step and pass one of its parameters, e.g. `META_MAINTENANCE_MERGE_ADJACENT_FILES_MAX_COMPACTED_FILES 50`. An `OLDER_THAN` interval is a rolling window, evaluated each pass. |
| `META_MAINTENANCE_COMPACT_STORE true` | Run a SlateDB compaction of the catalog store during maintenance. |

Steps are DuckLake maintenance functions without their `ducklake_`
prefix. In the order they run:

| Step | Parameters |
|---|---|
| `EXPIRE_SNAPSHOTS` | `OLDER_THAN`, `VERSIONS` |
| `FLUSH_INLINED_DATA` | |
| `MERGE_ADJACENT_FILES` | `MAX_COMPACTED_FILES` |
| `REWRITE_DATA_FILES` | `DELETE_THRESHOLD`, `MAX_COMPACTED_FILES` |
| `CLEANUP_OLD_FILES` | `OLDER_THAN`, `CLEANUP_ALL` |
| `DELETE_ORPHANED_FILES` | `OLDER_THAN`, `CLEANUP_ALL` |

After the DuckLake steps, the pass sweeps orphaned index entries, file
statistics, inline tables, and row summaries.

Outside of a scheduled run, `moraine_maintenance('lake')` can be used to run on
demand. `moraine_maintenance_status('lake')` reports the recent passes with each
step's outcome.

## Snapshot retention

Use `ducklake_expire_snapshots` to remove old snapshots and
`ducklake_cleanup_old_files` to delete files they no longer reference.
Configure both retention windows:

- The retention window of `ducklake_expire_snapshots` must exceed the
  longest read or open attach. Expiry deletes snapshot records, not data.
- The cleanup grace period, the `older_than` argument of
  `ducklake_cleanup_old_files`, must exceed the longest scan. Cleanup
  deletes the bytes no longer referenced by a snapshot.

A reader whose snapshot has been expired gets a `SnapshotExpired` error; a
workload that reaches back a fixed distance needs a retention window at least
that long.

## Encryption

Configure data-file encryption in DuckLake and catalog encryption on the
object-store bucket.

### Parquetfiles

Data-file encryption is managed by DuckLake. A lake attached `ENCRYPTED` gets a
key per Parquet file, generated by DuckLake and stored in the catalog. Moraine
stores those keys as given and performs no cryptography.

### Catalog

Table statistics and inlined rows live in catalog values rather than Parquet
files. They are protected only as well as the catalog is (not by DuckLake's
data-file encryption). To encrypt the catalog at rest, configure server-side
encryption and KMS-managed keys directly on the bucket.

The required grants depend on the attach mode. A writer needs to generate data
keys and decrypt them, `kms:GenerateDataKey` and `kms:Decrypt` in AWS terms. A
read-only attach needs `kms:Decrypt`.

## Backups and copies

A lake is three sets of objects: the catalog store, the write-ahead log (inside
the catalog store unless `META_WAL_PATH` is set), and the data files under
`DATA_PATH`. A backup is a plain copy of each prefix with the bucket's own
tooling, such as `aws s3 sync`; Moraine has no copy function. Asynchronous
bucket replication delivers objects in no particular order, so all three must
be copied at the same time, when no writer is attached.

When a lake is copied while a writer is running, objects may change under the
copy. If you do, create a checkpoint and attach the copy `READ_ONLY` with
`META_CHECKPOINT` naming it; that reads a fixed cut the copy is guaranteed to
hold. Do not open such a copy read-write.

A copy restored to the original prefixes attaches as before. A copy at new
prefixes needs one more step, because the lake records its data root and
refuses an attach that names a different one:

1. Detach the source lake everywhere, and stop any maintenance against it.
   If its log is on a separate store, move it into the catalog store first
   with `moraine_move_wal`, so the copy does not share a log with the
   original.
2. Copy the catalog prefix and the data prefix, keeping the object keys
   relative to each.
3. Point the copy at its new data root, with nothing attached to it:

   ```sql
   CALL moraine_rewrite_data_path('s3://destination/catalog',
                                  's3://source/data/',
                                  's3://destination/data/');
   ```

4. Attach the copy with the new `DATA_PATH`.

The rewrite changes only the recorded root. Files registered under relative
paths, retained snapshots and delete files included, resolve under the new
root; files registered by absolute path keep pointing where they were. The
[extension surface](/rfcs/0006-extension-surface/#relocating-a-copied-lake)
design document has the details.

## Upgrading

Check the extension build, store format, and DuckLake catalog version before
upgrading. The [release notes](/releases/) lists compatibility and breaking
changes for each release.

**The extension build.** Each build loads only into the DuckDB version it
was built for.

**The on-disk format.** A Moraine build opens any store within the range of
formats it reads. A store below that range is refused at attach with a
message naming `moraine_migrate`. Detach the lake from every process
before running it:

```sql
SELECT from_format, to_format, units_run, resumed
FROM moraine_migrate('s3://bucket/prefix');
```

A migration is resumable, one-way, and runs under the writer lock, so it
fences a running writer. Once a store is migrated, builds that predate the
new format refuse it: upgrade every process that attaches the lake before
migrating. `moraine_raise_format('lake', dry_run := true)` reports whether
an attached store can be stamped to a newer format without a rewrite, and
with `dry_run := false` does so.

**The DuckLake catalog version.** New lakes record DuckLake catalog version
`1.0`. Raising it to `1.1` is irreversible and requires `confirm => true`:

```sql
SELECT * FROM moraine_raise_catalog_version('lake', dry_run => true);
SELECT * FROM moraine_raise_catalog_version('lake', confirm => true);
```
